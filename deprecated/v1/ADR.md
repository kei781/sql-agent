# SQL Bot — 아키텍처 결정 기록 (ADR)

> `sqlbot` 설계 과정에서 내린 주요 결정을 기록한다. 각 ADR은 맥락·결정·결과·기각한 대안을 담는다.
> 형식: Nygard ADR. 상태는 모두 **채택됨**(2026-06-03). PRD와 교차 참조.

## 색인
- **ADR-001** LLM을 SQL 생성에 한정하고 실행·데이터 경로 분리
- **ADR-002** 인터페이스로 Slack 채택, `thread_ts` 기반 세션 격리
- **ADR-003** Intent spec + 코드 게이트로 명확화(재질문) 강제
- **ADR-004** 단일 카탈로그를 메타데이터 소스로, 기간을 테이블 속성으로
- **ADR-005** PII 마스킹을 DB 경계(마스킹 뷰 + 뷰 한정 읽기 롤)에서 강제
- **ADR-006** 실행 안전장치 — 읽기 전용 롤 + 런타임 가드, EXPLAIN은 최적화 필터
- **ADR-007** 실행 전 확인과 실행 후 감사를 별도 기능으로 분리
- **ADR-008** 진단 로그를 요청당 JSON(`./log`)으로, 집계는 비목표

---

## ADR-001: LLM을 SQL 생성에 한정하고 실행·데이터 경로를 분리

**상태**: 채택됨 · 2026-06-03

**맥락**
비개발자가 자연어로 사내 데이터를 조회한다. LLM이 쿼리 실행이나 결과 데이터까지 다루면 (1) 실데이터가 LLM(특히 외부 LLM)에 노출되고, (2) 제어 흐름이 LLM의 비결정적 판단에 의존하게 된다.

**결정**
LLM의 역할을 **자연어 → SQL 텍스트 생성**까지로 한정한다.
- 쿼리 실행은 서버사이드 코드가 수행.
- 결과는 CSV로 추출해 지정 채널에 직접 전달.
- LLM은 반환된 데이터에 접근하지 않는다.

**결과**
- (+) 실데이터가 LLM 경계를 넘지 않아 외부 LLM 사용이 정당화됨(스키마만 전달).
- (+) 게이트 통과·실행 판단이 결정론적 코드에 위치.
- (−) LLM이 결과를 보고 후속 보정·요약을 할 수 없음(설계상 의도된 제약).

**기각한 대안**
- LLM이 실행·결과 해석까지 담당 → 데이터 노출 + 비결정성으로 기각.

## ADR-002: 인터페이스로 Slack 채택, `thread_ts` 기반 세션 격리

**상태**: 채택됨 · 2026-06-03

**맥락**
비개발자 접근성이 중요하고, 한 채널에서 여러 사용자가 동시에 요청한다. 대화가 섞이지 않아야 한다. 별도 웹 프론트는 인증·배포 부담이 있다.

**결정**
Slack 봇을 인터페이스로 채택한다.
- 진입: `/sqlbot` 슬래시 → 모달 → submit 시 봇이 채널에 부모 메시지 게시 → 그 `thread_ts`가 세션 키.
- 이후 대화는 스레드 답글(Events API).
- 세션 상태는 서버사이드 스토어(Redis 등)에 `thread_ts`로 키잉.
- Events API 3초 ack 제약 때문에 LLM/SQL/CSV는 비동기 워커로 분리, `event_id`로 멱등 처리.

**결과**
- (+) `thread_ts` 단위로 동시성 격리가 자연히 확보됨(한 유저 다중 스레드 = 다중 세션).
- (+) 별도 프론트 불필요, 오프보딩은 Slack/SSO 비활성화로 해결.
- (−) 3초 ack 제약으로 모든 무거운 작업이 비동기 필수.
- (−) 회사 고정 IP 화이트리스트(웹앱 전제)가 최종 사용자에 적용되지 않음 → 인증 모델 재정의 필요(미해결).

**기각한 대안**
- 웹앱(기존 설계) → 별도 인증·프론트 부담으로 보류.
- 채널 본문 직접 대화 → 다중 사용자 대화가 섞여서 기각.

## ADR-003: Intent spec + 코드 게이트로 명확화(재질문) 강제

**상태**: 채택됨 · 2026-06-03

**맥락**
비개발자는 스키마를 모르고 SQL을 읽지 못한다. 가장 큰 위험은 에러가 아니라 **그럴듯하게 틀린 데이터**다(사용자가 검증하지 못하고 믿는다). LLM에게 "반드시 확인 질문하라"고 프롬프트로 지시하면 확률적으로 건너뛴다.

**결정**
요구사항을 SQL 직전에 **구조화된 intent spec**(지표/그룹핑/기간/필터)으로 먼저 채우고, 게이트를 **코드**에 둔다.
- LLM은 spec 슬롯 채우기만 담당.
- 코드가 필수 슬롯을 검사 → 비었거나 모호하면 그 턴은 무조건 질문 턴(SQL 경로 도달 불가).
- spec 완성 + 사용자 확인 후에만 SQL 생성 잠금 해제.
- 확인 메시지는 채워진 spec에서 렌더(비즈니스 용어). 답할 수 있는 모호성은 질문, 답할 수 없는 결정(조인 경로 등)은 시스템이 정하고 통보.
- 입력은 폼(공통 슬롯) + 자유 입력(복잡 필터) 하이브리드.

**결과**
- (+) "반드시 확인"이 프롬프트가 아니라 상태머신으로 강제됨.
- (+) 확인 메시지가 spec에서 렌더되어 가정 누락이 구조적으로 차단됨.
- (+) 비개발자에게 검증 가능한 단일 면(평문 요약)을 제공.
- (−) 폼이 표현하지 못하는 요구는 자유 입력 + 추가 재질문 필요.
- (−) 게이트 조건이 "한 번 물었나"가 아니라 "spec 완성됐나"라 반복 질문이 발생할 수 있음.

**기각한 대안**
- 프롬프트 기반 "항상 확인" → 확률적 누락으로 기각.
- 자연어 → 바로 SQL → 모호성 검출 지점이 없어 기각.

## ADR-004: 단일 카탈로그를 메타데이터 소스로, 기간을 테이블 속성으로

**상태**: 채택됨 · 2026-06-03

**맥락**
지표 정의·조인 경로·기간 제한·노출 대상이 여러 곳에 흩어지면 일관성이 깨진다. 특히 기간을 LLM이 매 요청마다 추론하면("매출은 1년이 적당") 같은 질문에 다른 결과가 나온다.

**결정**
테이블/뷰 메타데이터를 **단일 카탈로그**(버전 관리되는 config)로 두고 LLM·가드레일·spec 폼이 공통 소비한다.
- 항목: 비즈니스 설명, 컬럼 의미, 조인 경로, 지표 정의(예: 매출 = 결제일 기준), **시간 컬럼 + 기본 윈도우 + 최대 윈도우**.
- 기간은 카탈로그의 테이블 속성. 미지정 → 기본값 + 통보, 사용자 override, 최대 초과 → 캡.
- **카탈로그엔 마스킹된 뷰만 노출하고 원본 테이블은 제외**(ADR-005 연계).

**결과**
- (+) 기간·정의가 결정론적·일관적(LLM은 추론이 아니라 조회).
- (+) 카탈로그가 spec 폼의 선택지와 진단 로그 필드를 동시에 규정(단일 소스).
- (+) 원본 미노출로 LLM이 처음부터 뷰로만 SQL 작성.
- (−) 카탈로그 유지보수 부담(스키마 변경 시 동기화 필요).

**기각한 대안**
- 기간을 LLM이 매번 추론 → 일관성 결여로 기각.
- 원본 스키마를 LLM에 그대로 노출 → 권한 에러 유발 + 마스킹 약화로 기각.

## ADR-005: PII 마스킹을 DB 경계(마스킹 뷰 + 뷰 한정 읽기 롤)에서 강제

**상태**: 채택됨 · 2026-06-03

**맥락**
개인정보 보호가 필수다. 생성된 SQL은 신뢰할 수 없다 — 출력 컬럼명으로 마스킹하면 LLM이 별칭(`... AS x`)이나 `CONCAT` 파생으로 가공하는 순간 깨진다. 운영 DB는 MySQL Community Edition이다.

**결정**
마스킹을 애플리케이션이 아니라 **DB 경계**에서 강제한다.
- 마스킹된 뷰를 만들고, 읽기 전용 롤을 **뷰에만** grant, 원본 테이블은 grant하지 않는다.
- MySQL Community엔 동적 마스킹이 없으므로(Enterprise 기능) **뷰 정의에 마스킹 식을 직접 작성**.
- grant는 **테이블 단위**로(`GRANT SELECT ON db.v_users`), `GRANT ... ON db.*`는 금지. `SHOW GRANTS`로 원본 미포함 확인.

**결과**
- (+) 생성 SQL이 무엇이든(별칭/파생 포함) DB 경계에서 마스킹이 강제됨.
- (+) 외부 LLM에 주는 스키마가 이미 마스킹 뷰 스키마 → 스키마 노출 우려 해소.
- (+) 4단계 프로세스에 별도 마스킹 단계 불필요(런타임 → 뷰 정의로 위치 이동).
- (−) 뷰가 경직적 — 정당하게 원본이 필요한 케이스는 별도 경로 필요.
- (−) 준식별자 조합 재식별은 컬럼별 마스킹으로 막히지 않음(필요 시 구간화).
- (−) 마스킹 식을 수동으로 유지해야 함.

**기각한 대안**
- 출력 컬럼명 매칭 마스킹 → 별칭/파생에 깨져서 기각.
- 앱 레이어 마스킹 → SQL 우회로 뚫려서 기각.
- MySQL Enterprise 동적 마스킹 → 라이선스 비용으로 보류.

## ADR-006: 실행 안전장치 — 읽기 전용 롤 + 런타임 가드, EXPLAIN은 최적화 필터

**상태**: 채택됨 · 2026-06-03

**맥락**
무거운 쿼리가 운영 DB에 부하를 준다. 처음엔 `EXPLAIN` 비용으로 사전 차단하려 했으나, plain EXPLAIN cost는 옵티마이저 **추정값**이라 통계가 오래됐거나 상관 조건이면 크게 틀어진다. `EXPLAIN ANALYZE`는 실제로 쿼리를 실행하므로 사전 게이트로 쓰면 자기모순이다.

**결정**
- 실행 계정은 **읽기 전용 롤**(SELECT만, DDL/DML 권한 없음) + SELECT-only/단일문 파싱(다중문·데이터 변경 CTE·파일 함수 차단).
- 부하 안전장치는 **실행 단계 런타임 가드**: `statement_timeout`, 행 수 상한, CSV 바이트 상한.
- `EXPLAIN`은 "싼 건 빨리 통과"시키는 **최적화 1차 필터**로만 사용. 판단은 결정론적 코드(`EXPLAIN FORMAT JSON` 파싱 → cost/rows 임계 비교), LLM이 아님.

**결과**
- (+) 추정이 틀려 무거운 쿼리가 통과해도 런타임에서 차단됨.
- (+) DDL/DML이 권한 수준에서 원천 불가.
- (−) `EXPLAIN ANALYZE`를 게이트로 쓸 수 없음(실행되므로).
- (−) 런타임 가드 임계값 튜닝이 필요.

**기각한 대안**
- EXPLAIN cost를 차단 게이트로 → 추정값 + 자기모순으로 기각.
- LLM이 부하를 판단 → 비결정성으로 기각.

> 연계: 읽기 롤의 "뷰에만 grant"는 ADR-005(개인정보 경계), 여기서는 "읽기 전용·SELECT-only"라는 실행 안전 측면.

## ADR-007: 실행 전 확인과 실행 후 감사를 별도 기능으로 분리

**상태**: 채택됨 · 2026-06-03

**맥락**
"확인 질문"과 "CSV에 SQL+이유 첨부"는 비슷해 보이지만 푸는 문제가 다르다. 전자는 실행 전 정확성, 후자는 실행 후 기록이다. 후자는 데이터가 이미 나온 뒤라 정확성을 보장하지 못한다.

**결정**
두 기능을 **독립적으로** 둔다.
- (A) 실행 전 확인 = 정확성 안전장치(ADR-003).
- (B) 실행 후 기록 = 감사/진단. 목적은 **피드백 루프** — 비개발자가 "이 숫자 이상하다"고 가져오면 개발자가 기록으로 해석 오류를 진단해 카탈로그/프롬프트를 개선.
- (B)는 (A)를 대체하지 않는다.

**결과**
- (+) 각 기능의 책임이 명확(정확성 vs 추적).
- (+) (B)가 에이전트 점진 개선 메커니즘으로 기능함.
- (−) 두 기능을 따로 구현·유지해야 함.

**기각한 대안**
- 사후 SQL+이유로 정확성까지 보장 → 데이터가 이미 전달된 뒤라 불가능하여 기각.

## ADR-008: 진단 로그를 요청당 JSON 파일(`./log`)으로, 집계는 비목표

**상태**: 채택됨 · 2026-06-03

**맥락**
ADR-007의 (B) 기록을 어디에 어떻게 쌓을지 정해야 한다. 진단(개발자가 한 건 펼쳐보기)과 집계(패턴 분석)는 다른 요구다. 현 단계에서 필요한 것은 진단이다.

**결정**
- 기록은 **요청당 JSON 파일**, 경로 `./log/{thread_ts}_{ts}.json`.
- 내용: 원문 질문 / 채워진 spec / 확인 Q&A / 생성 SQL / 실행 메타(적용 기간·행 수·시각·요청자).
- **진단 전용. 집계는 현 단계 비목표** — 필요해지면 JSONL 또는 테이블로 이전.
- LLM이 쓰는 "이유"가 아니라 spec에서 출처를 렌더(LLM 재설명 안 시킴).

**결과**
- (+) 요청당 파일이라 동시 쓰기 race 없음, 한 건 진단에 단순·충분.
- (+) SQL만이 아니라 해석 단계(spec, Q&A)가 남아 "문법은 맞고 해석이 틀린" 케이스를 진단 가능.
- (−) 흩어진 파일이라 집계가 번거로움(현 단계 비목표라 수용).
- (−) `./log`는 재배포/컨테이너 재생성에 휘발 → 영속화 방식 확정 필요(미해결).
- (−) 원문 질문에 PII가 섞일 수 있음 → 보존기간 자동삭제 필요(미해결).

**기각한 대안**
- 감사 테이블(집계 가능) → 현 단계 진단만 필요해 보류(추후 이전 가능).
- Slack 메시지로만 기록 → 삭제 가능해 불변 감사기록으로 부적격하여 기각.
