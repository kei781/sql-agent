# SQL Bot PRD — 사내 데이터 셀프서비스 봇

> 가칭 `sqlbot`. 비개발자가 Slack에서 자연어로 사내 데이터를 조회해 CSV로 받는 도구.
> 이 문서는 설계 논의에서 확정된 내용을 정리한 것이며, 미해결 항목은 §11에 별도 명시.

---

## 1. 배경 / 문제

- 비개발자(운영·기획·CS)가 데이터가 필요할 때마다 데이터팀/개발팀에 ad-hoc 요청을 넣어 병목이 생김.
- 기존 시도는 외부 LLM(예: Claude 프로젝트)에 스키마를 통째로 박은 SQL 생성 챗봇이었음. 두 가지 문제:
  - 외부 LLM 인프라에 사내 데이터 모델이 상주 → 데이터 거버넌스 리스크.
  - 실행·권한·마스킹·감사 레이어가 없음(SQL 텍스트만 뱉고 끝).
- 목표: **자연어 → SQL → 실행 → CSV** 흐름을 권한·가드레일·마스킹·감사 위에서 안전하게 셀프서비스화.

---

## 2. 목표 / 비목표

**목표**
- 비개발자가 SQL을 몰라도 데이터를 직접 조회.
- "그럴듯하게 틀린 데이터"를 받는 사고 방지 — 실행 전 비즈니스 용어로 의도 확인.
- 개인정보 보호: DB 경계 마스킹 + 접근 권한 분리 + 감사 기록.
- 운영 DB 보호: 무거운 쿼리를 런타임에서 차단.

**비목표**
- 개발자가 임의 SQL을 자유롭게 쓰는 도구가 아님(그건 직접 DB 접근).
- BI 대시보드/시각화가 아님(CSV 추출까지).
- 실시간 스트리밍/대용량 ETL이 아님.

---

## 3. 대상 사용자

| 페르소나 | 특성 | 주 시나리오 |
|---|---|---|
| 운영 매니저 | SQL 미숙, 정기 지표 확인 | 일/주간 조회, 단건 조회 |
| 기획자·PM | 기본 SQL 가능, 복잡 JOIN 어려움 | 가설 검증용 추출 |
| CS 담당자 | 단건 조회 빈도 높음 | 고객 문의 대응 |
| 데이터팀 | 검토/승격 권한(Phase 2) | 세션 검증·공식화 |

---

## 4. 핵심 흐름

**4단계 로직**
1. 카탈로그(테이블·컬럼·관계)를 LLM이 읽고 SQL 작성.
2. SQL → `EXPLAIN`으로 비용 추정(1차 필터)으로 부하 측정.
3. 적정하면 실행 + CSV 추출.
4. 지정 채널에 CSV 자동 반환. **LLM은 반환된 데이터에 접근 불가.**

**Slack 인터랙션**
- `/sqlbot` → 모달 → submit → 봇이 채널에 부모 메시지 게시 → 그 메시지 스레드가 세션.
- 스레드 안에서 intent spec 슬롯 채우기(질문/확인) → 확정 → 실행 → CSV 회신.

## 5. 기능 요구사항

### 5.1 Slack 인터페이스 & 동시성
- 진입점: `/sqlbot` 슬래시 커맨드 → `views.open` 모달(트리거 토큰으로 ~3초 내 응답).
- 모달 submit → 봇이 채널에 부모 메시지 게시 → 그 `ts` = `thread_ts` = **세션 키**.
- 이후 모든 슬롯 채우기/확인은 **스레드 답글(Events API)**. 봇은 자기 스레드 답글을 `@멘션` 없이 청취.
- 동시성 격리: `thread_ts` 단위로 세션이 분리됨. 한 유저가 스레드 여러 개 = 세션 여러 개, 문제없음.
- 상태 스토어(Redis 등)를 `thread_ts`로 키잉: 대화 히스토리 / 채우는 중인 spec / 단계 / 요청자 `user_id`.
- **3초 ack 의무**: Events API는 3초 내 ack 필요 → LLM/SQL/CSV는 인라인 불가 → 비동기 워커로 분리, 결과는 `chat.postMessage`로 스레드 회신.
- **멱등성**: Slack은 타임아웃 시 이벤트 재전송 → `event_id`로 dedupe(안 하면 같은 쿼리 중복 실행).
- 주의: 슬래시 커맨드(모달)와 스레드 답글(Events)은 **다른 surface**. 3초 ack/dedupe/비동기는 후자에 해당.

### 5.2 카탈로그 (메타데이터)
- 정의: **"뭐가 가능한가."** 개발자가 한 번 정의, 모든 요청에 공통, 버전 관리되는 config. → 규칙집.
- 테이블/뷰별 항목:
  - 비즈니스 설명
  - 컬럼 + 의미
  - 조인 경로(relation)
  - 시간 컬럼 + 기본 윈도우 + 최대 윈도우
  - 지표 정의(예: 매출 = 결제일 기준 `SUM(amount)`)
- **카탈로그엔 마스킹된 뷰만 노출. 원본 테이블(`users` 등)은 제외.**
  - 이유: 원본이 노출되면 LLM이 원본으로 SQL을 짬 → 실행 시 권한 에러 → 사용자가 "왜 안 돼요" 헤맴.
  - 권한(DB 경계)이 안전장치, 카탈로그(LLM 입력)는 그걸 안 건드리게 하는 안내. **둘 다 필요.**
- LLM·가드레일·spec 폼이 공통으로 소비.

### 5.3 Intent Spec & 명확화 하네스
- intent spec = **"이번에 뭘 원하나"**(지표/그룹핑/기간/필터). 요청마다 생성.
- 흐름: `카탈로그 → spec 폼 렌더 → 사용자가 채움 → 채워진 spec → SQL`.
- 입력 방식: **폼(공통 슬롯) + 자유 입력(복잡 필터) 하이브리드.** 폼이 필수 슬롯을 강제해 재질문을 선차단하고, 폼이 못 잡는 건(예: "환불 후 이탈한 고객만") 자유 입력 + 재질문으로.
- **게이트는 코드에 둔다(LLM 프롬프트 아님)**:
  1. LLM은 spec 슬롯 채우기만 담당.
  2. 코드가 필수 슬롯 검사 → 비었거나 모호 플래그면 그 턴은 무조건 질문 턴(SQL 경로 도달 불가).
  3. spec 완성 + 사용자 확인 → 그제서야 SQL 생성 잠금 해제.
  - "반드시 확인해" 같은 프롬프트 지시는 확률적으로 새므로 상태머신으로 강제.
- 질문 vs 통보:
  - 답할 수 있는 모호성(매출 = 주문일이냐 결제일이냐) → **질문**(비즈니스 용어로).
  - 답할 수 없는 결정(조인 경로 등) → 시스템이 정하고 **통보**.
- 확인 메시지: **채워진 spec에서 렌더링**(LLM이 가정을 누락하고 확인 안 시키는 일 차단). 평문 비즈니스 요약이 비개발자의 **유일한 검증면**.
- 게이트 조건 = "spec 완성됐나"(not "한 번 물었나"). 답이 새 모호성을 낳으면 다시 질문.

### 5.4 기간 산정
- 기간은 **카탈로그의 테이블 속성**(LLM이 매번 추론 X → 일관성 확보). LLM은 추론이 아니라 카탈로그에서 조회.
- 미지정 → 기본 윈도우 적용 + 통보 / 사용자 override 가능.
- 최대 윈도우 초과 → 캡 + 통보.
- 캡을 넘는 풀히스토리가 진짜 필요한 경우 → **별도 처리**(§11 미해결). **세션 승격과 무관**(한도 = 리소스 문제, 승격 = 신뢰 문제).

### 5.5 SQL 생성
- LLM은 카탈로그(마스킹 뷰 스키마 + 관계) 기반으로 **SELECT만** 작성.
- 재사용 대비 바인딩 파라미터 권장.
- LLM은 제어 경로에 들어오지 않음. 게이트 통과·실행 판단은 전부 코드.

### 5.6 부하 게이트 (EXPLAIN + 런타임 가드)
- **EXPLAIN은 최적화 1차 필터지 보안이 아님.**
  - plain `EXPLAIN` cost는 옵티마이저 **추정값** — 통계가 오래됐거나 상관된 조건이면 크게 틀어짐.
  - `EXPLAIN ANALYZE`는 실제로 쿼리를 실행함 → 사전 게이트로는 자기모순(막으려던 무거운 쿼리를 그대로 한 번 돌림).
  - 용도: "싼 건 빨리 통과"시키는 1차 필터.
- **진짜 안전장치 = 실행 단계 런타임 가드**(추정이 틀려 무거운 쿼리가 통과해도 죽임):
  - `statement_timeout`
  - 행 수 상한(LIMIT 강제 / fetch cap)
  - CSV 바이트 상한
- 게이트 판단은 **결정론적 코드**: `EXPLAIN FORMAT JSON` 파싱 → `Total Cost`/`Plan Rows` 임계 비교. **LLM에게 시키지 않음.**

### 5.7 실행 & 가드레일
- 읽기 전용 DB 롤: SELECT만, DDL/DML 권한 자체가 없음.
- 단일 문 / SELECT-only 파싱: 다중문(`;`), 데이터 변경 CTE, 파일 읽기 함수 등 차단.
- 읽기 전용 트랜잭션 + 위 타임아웃.
- 롤은 **마스킹 뷰에만 grant**(§5.9).

### 5.8 CSV 전달
- 결과 → CSV → 지정 채널에 `chat.postMessage`.
- **LLM은 반환된 데이터에 접근 불가**(실데이터 경로 분리).
- 대용량 결과 전달 방식은 미해결(§11).
- CSV 채널 잔류 = PII 보존 이슈 → 보존기간 정책 필요(§8).

### 5.9 PII 마스킹 (MySQL)
- 원칙: **DB 경계에서 마스킹** = 마스킹된 뷰 + 읽기 롤을 뷰에만 grant.
  - 생성 SQL이 무엇이든(별칭, `CONCAT`, 파생 컬럼) 마스킹을 못 뚫음.
- **MySQL Community Edition엔 동적 마스킹 기능이 없음**(Enterprise 유료 기능) → **뷰 정의에 마스킹 식을 직접 작성**.
  - 예: `name → CONCAT(LEFT(name,1),'**')`, email/phone는 부분 마스킹.
  - 마스킹 로직이 런타임 프로세스 → 뷰 정의로 이동(없어진 게 아니라 위치가 바뀐 것, 한 번 짜두면 끝).
- 우회 차단:
  - `GRANT SELECT ON db.*` **금지**(원본·뷰 전부 노출되어 마스킹 무의미).
  - 테이블 단위 grant: `GRANT SELECT ON db.v_users TO ...`. 원본 `db.users`는 절대 grant 안 함.
  - `SHOW GRANTS`로 원본 테이블이 안 끼었는지 확인.
- 카탈로그에 원본 테이블 제외(§5.2)로 보강.
- 준식별자 재식별 주의: 나이+성별+지역 등 조합은 컬럼별 마스킹으로 안 막힘 → 필요 시 뷰에서 구간화(나이 → 연령대).
- 부수 효과: 외부 LLM에 주는 스키마가 이미 **마스킹된 뷰 스키마** → "외부 LLM에 스키마 줘도 되나" 문제까지 해소.

### 5.10 감사 / 진단 로깅
- **두 개의 다른 기능이며 서로 대체 불가**:
  - (A) 실행 전 확인 = **정확성** 안전장치(§5.3).
  - (B) 실행 후 기록 = **감사/진단**.
- (B)의 목적: **피드백 루프**. 비개발자가 "이 숫자 이상한데요" → 개발자가 기록을 보고 해석이 어디서 틀어졌는지 진단 → 카탈로그/프롬프트 수정.
- 진단엔 **전체 결정 경로**가 필요(SQL만으론 부족 — 보통 문법은 멀쩡하고 해석이 틀림. 예: 결제일을 주문일로 해석):
  - 원문 질문 / 채워진 spec / 확인 Q&A / 생성 SQL / 실행 메타(적용 기간, 행 수, 시각, 요청자).
- 저장: **요청당 JSON 파일, `./log/{thread_ts}_{ts}.json`**. **진단 전용 — 현 단계 집계 안 함.**
  - 집계가 필요해지면 → JSONL 또는 테이블로 이전.
- LLM이 쓰는 "이유"는 사후 서술이지 충실한 기록이 아님 → spec에서 출처를 렌더(LLM에 재설명 시키지 않음). 진단 입력 = spec 필드 그대로.
- 미해결 주의(§11): `./log` 휘발(재배포/컨테이너 재생성), 원문 질문 내 PII 잔류(보존기간 자동삭제 필요).
- 감사 기록은 **서버사이드 불변** 저장이어야 함(Slack 메시지는 삭제 가능 → PII 접근기록으로 부적격).

## 6. 아키텍처

```
[Slack 사용자]
   │  /sqlbot (슬래시 → 모달)
   ▼
[Slack 앱 백엔드]  ── 3s ack · event_id dedupe · Slack 서명 검증
   │  스레드 답글(Events API)
   ├─▶ [상태 스토어 (Redis)]  thread_ts 키: 히스토리 / spec / 단계 / user_id
   │
   ├─▶ [비동기 워커]
   │      ├─▶ [LLM 추론]  ← 카탈로그(마스킹 뷰 스키마 + 관계)
   │      │      · intent spec 슬롯 채우기 → SQL(SELECT)
   │      ├─▶ [Intent Spec 엔진]  코드 게이트: 슬롯 검사 / 확인
   │      ├─▶ [부하 게이트]  EXPLAIN FORMAT JSON 파싱 → cost/rows 임계(코드)
   │      ├─▶ [SQL 실행]  읽기 롤(뷰 전용) · 런타임 가드(timeout/row/byte)
   │      │      ▼
   │      │   [MySQL]  마스킹 뷰만 grant (원본 테이블 미부여)
   │      ├─▶ [CSV 추출]
   │      └─▶ [채널 회신]  chat.postMessage  (LLM은 결과 데이터 접근 불가)
   │
   └─▶ [감사/진단 로그]  ./log/{thread_ts}_{ts}.json (요청당)
```

핵심 원칙: 실데이터·결과 row는 사내 경계 안에서만 이동하고, LLM에는 텍스트(스키마·SQL)만 오간다.

## 7. 인증 & 접근 제어

- **권한 주체**: Slack `user_id` → 회사 SSO/계정 매핑. 오프보딩 시 Slack 워크스페이스/SSO 비활성화로 접근 차단.
- **운영 범위**: 봇은 지정된 채널에서만 동작.
- **이벤트 진위**: Slack 서명 시크릿으로 이벤트가 Slack발인지 검증.
- **데이터 권한**: 읽기 롤은 마스킹 뷰에만 grant. 원본/민감 테이블 접근 불가.
  - 현재 모델은 **전 사용자 동일 뷰 권한**. 사용자별 데이터 차등(예: CS vs 재무)은 미해결(§11).
- 참고: 회사 고정 IP 화이트리스트는 웹앱 전제 개념이라 Slack 최종 사용자에는 적용되지 않음(§11).

## 8. 보안 & 개인정보 (DPO 관점)

- **외부 LLM 이전**: 실데이터 미전송 + 마스킹 뷰 스키마만 전달 → 국외이전/처리위탁 리스크 완화. 단, 컬럼명 자체가 민감 항목을 직접 드러내면 별도 검토.
- **PII 접근 기록**: 감사 로그(요청자/질문/SQL/행 수/시각)를 서버사이드 불변으로.
- **보존기간**: 채널 CSV, `./log` 모두 보존기간 정책 + 자동삭제 필요.
- **재식별 한계**: 마스킹해도 준식별자 조합으로 재식별 가능 — 인지 전제, 민감 조합 잦으면 구간화.
- **처리방침 반영**: 외부 LLM 수탁/이전 명시 여부 확인(대표=CPO, 담당=호크 구조 기준).

## 9. 단계별 (Phasing)

**MVP**
- `/sqlbot` → 모달 → 스레드 슬롯 채우기 → 확인 → EXPLAIN 1차 필터 + 런타임 가드 → 실행 → CSV 회신.
- 마스킹 뷰 + 읽기 전용 롤. 단일 DB.
- 요청당 JSON 진단 로그.

**Phase 2**
- 세션 승격(draft → verified → official, 신뢰 생애주기. 검증된 쿼리를 정식 리포트로).
- 파라미터화 재실행, 로그 집계, 다중 DB.

**Phase 3**
- 스케줄 실행 / 정기 배포(슬랙·이메일), 도메인 용어 사전 누적.

## 10. 핵심 설계 원칙 (의도적으로 분리해야 하는 것들)

설계 중 반복해서 헷갈렸던, 섞으면 안 되는 구분들:

- **EXPLAIN ≠ 보안.** EXPLAIN은 최적화 필터, 보안은 런타임 가드.
- **게이트 = 코드.** "반드시 확인해" 프롬프트는 확률적으로 샌다.
- **접속 인증 ≠ 데이터 권한.**
- **카탈로그(뭐가 가능, 1회 정의) ≠ intent spec(이번 요청, 매번).**
- **실행 전 확인(정확성) ≠ 실행 후 기록(감사).** 서로 대체 불가.
- **한도 초과(리소스) ≠ 세션 승격(신뢰).**
- **마스킹은 DB 경계(뷰 + grant)**, 출력 컬럼명 매칭이 아니다.
- **LLM은 텍스트(SQL)까지만**, 제어·실데이터 경로 밖.
