# SQL Bot — 아키텍처 결정 기록 (ADR)

> `sqlbot` 설계 과정에서 내린 주요 결정. 각 ADR은 맥락·결정·결과·기각한 대안을 담는다.
> 형식: Nygard ADR. 상태는 별도 표기 없으면 **채택됨**(2026-06-03). PRD와 교차 참조.
> **v2 (2026-06-03)** — 설계 리뷰 반영: ADR-001·006 보강, ADR-009~014 추가.

## 색인
- **ADR-001** LLM을 SQL 생성에 한정하고 실행·데이터 경로 분리 *(v2 보강)*
- **ADR-002** 인터페이스로 Slack 채택, `thread_ts` 기반 세션 격리
- **ADR-003** Intent spec + 코드 게이트로 명확화(재질문) 강제
- **ADR-004** 단일 카탈로그를 메타데이터 소스로, 기간을 테이블 속성으로
- **ADR-005** PII 마스킹을 DB 경계(마스킹 뷰 + 뷰 한정 읽기 롤)에서 강제
- **ADR-006** 실행 안전장치 — 읽기 전용 롤 + 런타임 가드, EXPLAIN은 최적화 필터 *(v2 MySQL 명세 수정)*
- **ADR-007** 실행 전 확인과 실행 후 감사를 별도 기능으로 분리
- **ADR-008** 진단 로그를 요청당 JSON(`./log`)으로, 집계는 비목표
- **ADR-009** 사용자별 데이터 권한 모델(catalog ACL) — *MVP 필드만, Phase 2 강제*
- **ADR-010** 결과(CSV) 전달과 보존 정책
- **ADR-011** SQL 검증/재작성 게이트
- **ADR-012** 평가(eval) 하네스
- **ADR-013** 외부 LLM provider 및 데이터 처리
- **ADR-014** PII 접근 감사 로그 — 진단 로그와 분리

## ADR-001: LLM을 SQL 생성에 한정하고 실행·데이터 경로를 분리

**상태**: 채택됨 · 2026-06-03 *(v2 보강)*

**맥락**
LLM이 쿼리 실행이나 결과 데이터까지 다루면 (1) 실데이터가 LLM(특히 외부 LLM)에 노출되고, (2) 제어 흐름이 LLM의 비결정적 판단에 의존한다.

**결정**
LLM의 역할을 **자연어 → SQL 텍스트 생성**까지로 한정한다. 실행은 서버사이드 코드, 결과는 채널/스토리지로 직접 전달, LLM은 반환 데이터에 접근하지 않는다.

**결과**
- (+) 실데이터(결과 row)가 LLM 경계를 넘지 않음.
- (+) 게이트·실행 판단이 결정론적 코드에 위치.
- (−) LLM이 결과를 보고 후속 보정·요약을 못 함(의도된 제약).

**기각한 대안**
- LLM이 실행·결과 해석까지 담당 → 데이터 노출 + 비결정성으로 기각.

**v2 보강 — 외부 LLM 사용 시의 한계**
본 ADR이 보장하는 것은 **결과 row 미반출**뿐이다. SQL 생성을 위해 **스키마·사용자 질문·생성 SQL은 외부 LLM으로 나가며**, 질문/SQL에 사람 이름·사명 등 식별자가 포함될 수 있다. 자유형 식별자는 입력에서 기술 마스킹이 불가능하므로(이름 NER 비신뢰, 사명 패턴 없음), 이 잔여 노출은 **차단하지 않고 계약+고지로 수용**한다(ADR-013).

## ADR-002: 인터페이스로 Slack 채택, `thread_ts` 기반 세션 격리

**상태**: 채택됨 · 2026-06-03

**맥락**
비개발자 접근성이 중요하고, 한 채널에서 여러 사용자가 동시에 요청한다. 대화가 섞이지 않아야 한다.

**결정**
Slack 봇. `/sqlbot` 슬래시 → 모달 → submit 시 봇이 부모 메시지 게시 → 그 `thread_ts`가 세션 키. 이후 대화는 스레드 답글(Events API). 상태는 서버사이드(`thread_ts` 키잉). 3초 ack 제약으로 무거운 작업은 비동기 워커 + `event_id` 멱등.

**결과**
- (+) `thread_ts` 단위 동시성 격리(한 유저 다중 스레드 = 다중 세션).
- (+) 별도 프론트 불필요, 오프보딩은 Slack/SSO 비활성화.
- (−) 3초 ack 제약으로 무거운 작업 비동기 필수.
- (−) 회사 고정 IP 화이트리스트가 최종 사용자에 적용되지 않음 → 서명 검증 + 워크스페이스 멤버십으로 대체.

**기각한 대안**
- 웹앱(기존 설계) → 별도 인증·프론트 부담으로 보류.
- 채널 본문 직접 대화 → 다중 사용자 대화가 섞여서 기각.

## ADR-003: Intent spec + 코드 게이트로 명확화(재질문) 강제

**상태**: 채택됨 · 2026-06-03

**맥락**
비개발자는 SQL을 검증하지 못한다. 가장 큰 위험은 에러가 아니라 **그럴듯하게 틀린 데이터**다. "반드시 확인 질문하라"는 프롬프트 지시는 확률적으로 건너뛴다.

**결정**
SQL 직전에 **구조화된 intent spec**(지표/그룹핑/기간/필터)을 채우고 게이트를 **코드**에 둔다. LLM은 슬롯 채우기만, 코드가 필수 슬롯 검사(비거나 모호하면 무조건 질문 턴), 완성 + 확인 후에만 SQL 잠금 해제. 확인 메시지는 채워진 spec에서 렌더(비즈니스 용어). 입력은 폼 + 자유 입력 하이브리드.

**결과**
- (+) "반드시 확인"이 상태머신으로 강제됨.
- (+) 확인 메시지가 spec 렌더라 가정 누락 차단.
- (−) 폼이 표현 못 하는 요구는 자유 입력 + 추가 재질문.
- (−) 게이트 조건이 "spec 완성"이라 반복 질문 발생 가능.

**기각한 대안**
- 프롬프트 기반 "항상 확인" → 확률적 누락으로 기각.
- 자연어 → 바로 SQL → 모호성 검출 지점 없어 기각.

## ADR-004: 단일 카탈로그를 메타데이터 소스로, 기간을 테이블 속성으로

**상태**: 채택됨 · 2026-06-03

**맥락**
정의·조인 경로·기간이 흩어지면 일관성이 깨진다. 기간을 LLM이 매번 추론하면 같은 질문에 다른 결과가 나온다.

**결정**
테이블/뷰 메타데이터를 **단일 카탈로그**(버전 관리 config)로 두고 LLM·가드레일·SQL 검증·spec 폼이 공통 소비. 항목: 비즈니스 설명, 컬럼 의미, 조인 경로, 지표 정의, **시간 컬럼 + 기본/최대 윈도우**. 기간은 테이블 속성(미지정→기본+통보, override, 최대 초과→캡). **카탈로그엔 마스킹 뷰만, 원본 제외**(ADR-005).

**결과**
- (+) 기간·정의가 결정론적·일관적.
- (+) 카탈로그가 spec 폼 선택지·진단 로그 필드를 동시에 규정(단일 소스).
- (−) 카탈로그 유지보수 부담.

**기각한 대안**
- 기간을 LLM이 매번 추론 → 일관성 결여로 기각.
- 원본 스키마를 LLM에 노출 → 권한 에러 + 마스킹 약화로 기각.

## ADR-005: PII 마스킹을 DB 경계(마스킹 뷰 + 뷰 한정 읽기 롤)에서 강제

**상태**: 채택됨 · 2026-06-03

**맥락**
생성 SQL은 신뢰할 수 없다(별칭·`CONCAT`·파생으로 출력 컬럼명 마스킹이 깨진다). 운영 DB는 MySQL Community Edition.

**결정**
마스킹을 **DB 경계**에서 강제. 마스킹 뷰 + 읽기 롤을 **뷰에만** grant, 원본 미부여. MySQL Community엔 동적 마스킹이 없어(Enterprise 기능) **뷰 정의에 마스킹 식 직접 작성**. grant는 테이블 단위(`db.*` 금지), `SHOW GRANTS`로 원본 미포함 확인(CI 체크 권장).

**결과**
- (+) 생성 SQL이 뭐든 DB 경계에서 마스킹 강제.
- (+) 외부 LLM에 주는 스키마가 마스킹 뷰 스키마 → 실데이터 이전 리스크 **완화**.
- (+) 별도 마스킹 프로세스 불필요(런타임 → 뷰 정의로 위치 이동).
- (−) 뷰 경직 — 정당하게 원본이 필요한 케이스는 별도 경로.
- (−) 준식별자 조합 재식별은 안 막힘(필요 시 구간화).
- (−) 마스킹 식 수동 유지.

**기각한 대안**
- 출력 컬럼명 매칭 마스킹 → 별칭/파생에 깨져서 기각.
- 앱 레이어 마스킹 → SQL 우회로 뚫려서 기각.
- MySQL Enterprise 동적 마스킹 → 라이선스 비용으로 보류.

## ADR-006: 실행 안전장치 — 읽기 전용 롤 + 런타임 가드, EXPLAIN은 최적화 필터

**상태**: 채택됨 · 2026-06-03 *(v2 MySQL 명세 수정)*

**맥락**
무거운 쿼리가 운영 DB에 부하. plain EXPLAIN cost는 **추정값**이라 통계가 오래됐거나 상관 조건이면 크게 틀어진다. `EXPLAIN ANALYZE`는 실제로 실행하므로 사전 게이트로 쓰면 자기모순.
*(v1은 런타임 가드와 EXPLAIN 필드를 PostgreSQL 용어로 잘못 기재했다. 본 버전에서 MySQL 기준으로 수정.)*

**결정**
- 실행 계정은 **읽기 전용 롤**(SELECT만) + 실행 직전 AST 검증(ADR-011).
- 부하 안전장치는 **런타임 가드(MySQL)**:
  - `SET SESSION max_execution_time = <ms>`(read-only SELECT에 적용) + 검증 통과 후 `/*+ MAX_EXECUTION_TIME(<ms>) */` 힌트 주입.
  - `LIMIT <row_cap + 1>` 강제, CSV byte cap, 워커 watchdog(`KILL QUERY`).
  - 타임아웃/캡 초과 시 사용자 친화 에러.
- `EXPLAIN`은 **최적화 1차 필터**로만. 문법 `EXPLAIN FORMAT=JSON`. **지원 버전 고정**(MySQL 8.0.x 또는 8.4 LTS) + 파서 fixture 테스트. cost=`query_block.cost_info.query_cost`, rows=`rows_examined_per_scan`/`rows_produced_per_join`. 뷰 EXPLAIN엔 `SHOW VIEW` 권한 필요 가능(ADR-011). 판단은 결정론적 코드, LLM 아님.

**결과**
- (+) 추정이 틀려 통과해도 런타임에서 차단.
- (+) DDL/DML이 권한 수준에서 원천 불가.
- (−) `EXPLAIN ANALYZE`를 게이트로 못 씀(실행되므로).
- (−) MySQL 버전에 EXPLAIN JSON 파서가 종속 → 버전 고정·fixture 필수.

**기각한 대안**
- EXPLAIN cost를 차단 게이트로 → 추정값 + 자기모순으로 기각.
- LLM이 부하 판단 → 비결정성으로 기각.
- `statement_timeout`(PostgreSQL) → MySQL엔 없음, `max_execution_time`로 대체.

## ADR-007: 실행 전 확인과 실행 후 감사를 별도 기능으로 분리

**상태**: 채택됨 · 2026-06-03

**맥락**
"확인 질문"과 "기록"은 비슷해 보이지만 문제가 다르다. 전자는 실행 전 정확성, 후자는 실행 후 기록이며, 후자는 데이터가 이미 나온 뒤라 정확성을 보장하지 못한다.

**결정**
독립 기능으로 둔다. (A) 실행 전 확인 = 정확성(ADR-003). (B) 실행 후 기록 = 감사/진단, 목적은 피드백 루프(개발자가 기록으로 해석 오류 진단 → 카탈로그/프롬프트 개선). (B)는 (A)를 대체하지 않는다.

**결과**
- (+) 책임 명확(정확성 vs 추적).
- (+) (B)가 에이전트 점진 개선 메커니즘으로 기능.
- (−) 두 기능을 따로 구현·유지.

**기각한 대안**
- 사후 SQL+이유로 정확성까지 보장 → 데이터가 이미 전달된 뒤라 불가능하여 기각.

## ADR-008: 진단 로그를 요청당 JSON 파일(`./log`)으로, 집계는 비목표

**상태**: 채택됨 · 2026-06-03

**맥락**
ADR-007의 (B) 기록을 어디에 쌓을지. 진단(한 건 펼쳐보기)과 집계(패턴 분석)는 다른 요구이며, 현 단계엔 진단이 필요하다.

**결정**
**요청당 JSON 파일** `./log/{thread_ts}_{ts}.json`. 내용: 원문 질문 / 채워진 spec / 확인 Q&A / 생성 SQL / 실행 메타. **진단 전용, 집계 비목표**(필요 시 JSONL/테이블로 이전). LLM "이유"가 아니라 spec에서 출처 렌더.

**결과**
- (+) 요청당 파일이라 동시 쓰기 race 없음, 한 건 진단에 단순·충분.
- (+) SQL만이 아니라 해석 단계(spec, Q&A)가 남아 "문법은 맞고 해석이 틀린" 케이스 진단 가능.
- (−) 흩어진 파일이라 집계 번거로움(현 단계 비목표라 수용).
- (−) `./log`는 재배포/변조에 취약.

**기각한 대안**
- 감사 테이블(집계 가능) → 현 단계 진단만 필요해 보류.
- Slack 메시지로만 기록 → 삭제 가능해 부적격.

> **주의**: 본 ADR은 **개발 진단**용 로그다. PII 접근 **감사**는 영속·불변 요건이 달라 **ADR-014에서 별도로** 다룬다. local `./log`를 감사로 겸용하지 않는다.

## ADR-009: 사용자별 데이터 권한 모델(catalog ACL)

**상태**: 채택됨(부분) · 2026-06-03 — **MVP는 필드 정의만, 강제는 Phase 2**

**맥락**
페르소나가 CS/운영/PM/데이터팀 혼합이고 단건조회와 재무 매출은 민감도가 다르다. 다만 **MVP는 신뢰 소수 파일럿**이라 전 사용자 균일 권한이 당장은 허용된다. 리뷰는 "Open Question으로 두기엔 위험"하다고 지적했고, 이는 대상 범위에 달려 있다.

**결정**
- catalog에 dataset별 **ACL 필드**(`allowed_roles`, `audit_level`, `require_reason`, `require_approval_over_rows` 등)를 정의한다.
- **MVP에선 필드만 두고 강제하지 않는다**(전 사용자 균일 뷰 권한). 강제는 Phase 2.
- 강제 시 매핑: Slack `user_id` → SSO role → catalog ACL → 실행 가능 dataset/metric. DB 권한은 최후 경계, **앱 ACL은 제품 정책**.
- 세션 행위자 권한(요청자만 spec 수정/confirm, 승인자 별도 role)은 **MVP에 포함**(ACL 강제와 무관하게 접근통제).
- **트리거**: 파일럿 범위 이탈(채널 확대, CS/재무 등 민감도 상이 그룹 합류) 시 ACL 강제를 차단요건으로 승격.

**결과**
- (+) 파일럿 단순, 구조는 미리 자리잡음(나중에 필드만 강제 on).
- (+) 행위자 권한은 즉시 확보되어 "남이 confirm" 시나리오 차단.
- (−) 강제 전까지 균일 권한이라 범위 관리가 운영 규율에 의존.

**기각한 대안**
- 처음부터 DB role 사용자별 완전 분리 → 파일럿엔 과함.
- 사용자별 권한을 Open Question으로 방치 → 범위 확대 시 위험하여 기각(트리거로 명시).

## ADR-010: 결과(CSV) 전달과 보존 정책

**상태**: 채택됨 · 2026-06-03

**맥락**
v1은 "CSV → `chat.postMessage`"라 기재했으나 그것은 메시지 API지 파일 업로드 플로우가 아니다. 기존 `files.upload`는 폐기됐다. CSV는 PII 잔류 위험이 있다.

**결정**
- **소형 결과**: Slack external upload — `files.getUploadURLExternal` → upload URL에 CSV bytes POST → `files.completeUploadExternal`로 채널/스레드 공유.
- **대형/민감 결과**: 사내 object storage + **짧은 TTL presigned URL**, 다운로드 시 **SSO 재검증**. Slack엔 파일 대신 메타 + 링크 게시.
- MVP에서 "Slack 잔류" vs "사내 링크" 중 **하나를 명시 선택**(PII면 후자 권장).
- CSV retention 정책 + 자동 삭제 job.

**결과**
- (+) 현행 Slack API 정합, PII 통제 선택 명확.
- (−) presigned URL 경로는 object storage·인증 추가 구현.

**기각한 대안**
- `files.upload` → 폐기되어 사용 불가.
- `chat.postMessage`로 파일 전달 → 메시지 API라 불가.

## ADR-011: SQL 검증/재작성 게이트

**상태**: 채택됨 · 2026-06-03

**맥락**
"LLM이 SELECT만 짠다"는 약속이지 보장이 아니다. 실행 직전 결정론적 검증이 필요하다.

**결정**
실행 전 **SQL AST validator**:
- 단일 statement, `SELECT`/`WITH ... SELECT`만 허용.
- `INSERT/UPDATE/DELETE/REPLACE/CREATE/DROP/ALTER/TRUNCATE/CALL/DO/LOAD DATA` 차단.
- `INTO OUTFILE`/`LOAD_FILE`/`SLEEP`/`BENCHMARK` 차단.
- `information_schema`/`mysql`/`performance_schema`/`sys` 차단.
- **카탈로그 등록 뷰만** `FROM`/`JOIN`. `SELECT *` 금지(또는 컬럼 수 제한). `LIMIT` 강제.
- join 조건 없는 JOIN/cross join 차단, `ORDER BY` 없는 대용량 결과 경고.
- **재작성 순서**: LLM 주석/힌트 제거 → 검증 → **통과 후** 가드 힌트(`MAX_EXECUTION_TIME`)·`LIMIT` 주입.
- 권한: 읽기 롤이 EXPLAIN·실행 모두 수행(뷰 EXPLAIN에 `SHOW VIEW` 필요 시 부여). 분리가 필요하면 planner role 별도. MVP는 단일 읽기 롤로 단순화.

**결과**
- (+) LLM 생성과 무관한 결정론적 안전장치(SELECT-only 약속과 별개 층).
- (−) AST 파서 유지(MySQL 방언), 오탐 시 정당 쿼리 차단 가능.

**기각한 대안**
- LLM 약속에만 의존 → 보장이 아니라 기각.

## ADR-012: 평가(eval) 하네스

**상태**: 채택됨 · 2026-06-03

**맥락**
사후 진단 루프(ADR-007/008)는 있으나 **배포 전 품질 게이트**가 없다. 카탈로그/프롬프트 변경이 회귀를 일으켜도 배포 후에야 발견된다.

**결정**
**golden question set**(최소 50~100)을 구축한다. 각 항목에 expected spec / expected SQL 패턴 / 기대 모호성 질문을 저장. 예: "지난주 결제 매출", "환불 제외 매출", "가입 후 7일 내 구매 전환율", "특정 고객 단건 조회". 배포 전 **회귀 게이트**로 실행(spec/SQL/재질문 회귀 검사).

**결과**
- (+) 카탈로그/프롬프트 변경의 회귀를 배포 전 차단.
- (−) golden set 구축·유지 비용.

**기각한 대안**
- 사후 진단만으로 품질 관리 → 이미 배포된 뒤라 늦어서 기각.

## ADR-013: 외부 LLM provider 및 데이터 처리

**상태**: 채택됨 · 2026-06-03

**맥락**
SQL 생성에 **외부 LLM**을 쓴다(LLM을 SQL 생성으로 한정한 이유). 실데이터(결과 row)는 미반출하나 **스키마·질문·생성 SQL은 외부로 나간다**. 질문/SQL에 사람 이름·사명 등 식별자가 포함될 수 있다. 자유형 식별자는 입력에서 마스킹이 불가능하다(사람 이름 NER 비신뢰, 사명은 패턴 자체가 없음. 정형 PII만 regex로 잡히나 부분 차단은 보장이 아니다).

**결정**
외부 LLM을 사용한다. **입력단 PII 마스킹은 추진하지 않는다**(자유형 식별자 차단 불가). 대신 **계약 + 고지로 리스크 수용**:
- **학습 미사용**이 약관/DPA에 문서화된 **티어** 사용(무료/일반 티어는 학습 사용 가능성 — **티어 확인 필수**). 구두 보장이 아니라 문서.
- 외부 **retention**(로그 보존) 확인, region 고정(가능 시).
- 개인정보 **처리방침에 국외이전 명시**(수탁자명/이전국가/항목). **이 고지가 리스크 수용의 법적 근거** — 미고지 시 미고지 위반이 된다.
- 사명은 대개 개인정보가 아님(법인) → 이미 "스키마 외부 전송" 결정에 포함된 영업비밀 카테고리.

**결과**
- (+) 기술로 못 막는 잔여 노출을 계약/고지로 닫음(어차피 스키마 전송에 필요한 계약).
- (−) provider 약관·티어·region에 종속, 처리방침 갱신 의무.

**기각한 대안**
- 입력 PII 마스킹으로 차단 → 자유형 이름/사명 마스킹 불가로 기각.
- 로컬 LLM → 데이터주권엔 유리하나 현 결정은 외부(추후 재검토 대상).

## ADR-014: PII 접근 감사 로그 — 진단 로그와 분리

**상태**: 채택됨 · 2026-06-03

**맥락**
ADR-008의 진단 로그는 local JSON(dev 편의)로 충분하나, **PII 접근 감사로는 부적격**이다(컨테이너 재배포·삭제·변조에 취약). Slack 메시지도 삭제 가능. DPO 관점에서 PII 접근 기록은 사실상 의무에 가깝다(원문 질문에 개인정보가 섞일 수 있음).

**결정**
진단 로그와 **별도로** 영속·불변 감사 로그를 운영한다.
- append-only DB table 또는 object storage, **server-side 암호화**, retention + 삭제 job.
- 필드: `request_id`, `thread_ts`, `requester`, `approver(confirmed_by/at)`, `catalog version`, `spec hash`, `SQL hash`, `row count`, `byte count`, `result object id`, 시각.
- 원문 질문은 PII 가능성 → 별도 암호화 필드 또는 redaction.

**결과**
- (+) PII 접근의 불변 추적, 법적 요건 충족.
- (−) 별도 저장소·암호화·보존 운영 부담.

**기각한 대안**
- local `./log`를 감사로 겸용 → 변조·휘발로 부적격하여 기각.
- Slack 메시지를 감사 기록으로 → 삭제 가능해 부적격하여 기각.
